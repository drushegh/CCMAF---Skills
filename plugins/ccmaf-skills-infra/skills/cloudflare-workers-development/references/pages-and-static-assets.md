# Pages, static assets, `_headers` and `_redirects`

## Pages or Workers static assets?

| | Workers + static assets | Pages |
|---|---|---|
| New project | Default choice — one product, one config | Fine for a pure static site already on Pages |
| Server code | The Worker itself | Pages Functions (`functions/` file routing) or `_worker.js` |
| Cron, Queues consumers, Workers Logs, gradual deploys, `--remote` dev | Yes | No |
| Custom domain outside a Cloudflare zone | No | Yes |
| Git integration | Workers Builds | Pages git integration |

Cloudflare publishes a Pages → Workers migration guide and notes Workers has
"a distinctly broader set of features". Both read `_headers` and
`_redirects` from the asset directory.

Workers static assets config:

```jsonc
"assets": {
  "directory": "./dist",
  "binding": "ASSETS",                       // optional: env.ASSETS.fetch(req)
  "not_found_handling": "single-page-application",
  "run_worker_first": ["/api/*", "!/api/docs/*"] // default false: assets win
}
```

By default a matching static file is served **without running the Worker** —
auth checks in the Worker do not protect static files unless
`run_worker_first` covers those paths.

## Git integration deploys regardless of CI

A git-connected Pages project deploys "every time you push a change to a
branch" — production for the production branch, previews for the others —
with no knowledge of your CI. A failing test run does not stop the deploy.
Make CI a real gate by one of:

1. **Branch protection**: require CI checks before merge to the production
   branch and block direct pushes (free on public repos; check your git
   host's plan for private repos).
2. **Disable automatic production deployments** (*Build > Branch control*)
   and deploy from CI after tests: `wrangler pages deploy ./dist
   --project-name <name> --branch main`.
3. **Direct Upload only** — create the project without git integration and
   deploy from CI. A project created with git integration **cannot be
   switched to Direct Upload** later; decide at creation.

Preview branches can be disabled or restricted the same way. Skipping a build
with a commit-message marker is supported (verify the exact marker) but is
not a gate.

## `_headers`

- Place in the build output (asset) directory. Up to **100 rules**, **2,000
  characters per line**.
- Rules are URL patterns with one `*` splat (`:splat`) or named placeholders
  (`:slug`), each followed by indented `Header: value` lines.
- **Duplicates are comma-joined, not replaced**: the same header set twice —
  by repeated lines or by two rules whose patterns both match — is sent as
  one header with both values. Two `Content-Security-Policy` values joined
  this way enforce **both** policies (stricter than either). Keep exactly
  one CSP rule per path and use `! Content-Security-Policy` (bang + space)
  to detach a site-wide header on a sub-path before setting a new one.
- **Not applied** to responses generated by Pages Functions or Worker code —
  set headers in code there. Redirects run before headers.
- Framework preview servers (`astro preview`, `vite preview`, `next start`)
  and plain static servers **ignore `_headers`**. Verify on a preview
  deployment:

```bash
curl -sI https://<preview>.<project>.pages.dev/ | grep -i -E "content-security-policy|strict-transport|x-frame"
```

  and keep a post-deploy smoke test that asserts the CSP is present and
  appears once.

Example (fictional):

```
/*
  X-Content-Type-Options: nosniff
  Referrer-Policy: strict-origin-when-cross-origin
  Content-Security-Policy: default-src 'self'; img-src 'self' data:; frame-ancestors 'none'

/embed/*
  ! Content-Security-Policy
  Content-Security-Policy: default-src 'self'; frame-ancestors https://partner.example
```

## `_redirects`

- Pages limit: 2,000 static + 100 dynamic rules (2,100 total). Format:
  `/old /new 301`; splats and placeholders allowed; first match wins.
- Proxying (`200` rewrites) works only to paths on the same site (verify).
- Redirect loops and SPA fallbacks fight: with
  `not_found_handling: "single-page-application"` (Workers) or Pages' SPA
  default, don't add a catch-all `/* /index.html 200`.

## Pages Functions

- `functions/` directory maps files to routes (`functions/api/recipes/[id].ts`).
  Handlers export `onRequest`/`onRequestGet` etc. and receive `context.env`
  bindings configured for the Pages project.
- Requests to Functions count as Workers requests against the same daily
  free quota (verify); static asset requests that don't invoke a Function do
  not.
- `_routes.json` controls which paths invoke Functions — exclude static paths
  so they never burn Function invocations.
- Moving to Workers: `wrangler pages functions build` compiles `functions/`
  into one Worker script.

## Preview deployments

Every non-production branch push gets a unique preview URL. Previews use the
**preview environment's** bindings and variables — set them separately, and
don't point previews at the production D1 database. Protect previews that
expose unreleased data with Cloudflare Access (free for small teams — verify
seat limits).
