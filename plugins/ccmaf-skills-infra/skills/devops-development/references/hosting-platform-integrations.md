# Hosting-Platform Git Integrations (Cloudflare, Vercel, Netlify)

Static and edge hosts usually ship a "connect your repo" integration
that builds and deploys on push. It is convenient and it quietly sits
**outside** your CI pipeline, which changes what CI can promise.
Platform mechanics for Cloudflare live in
`cloudflare-workers-development`; this file is about the CI/CD shape.

## CI is not a gate unless you make it one

A git-integrated Cloudflare Pages project deploys the production branch
on every push — Cloudflare's docs say it deploys "every time you push a
change to a branch", with no reference to CI status. Vercel and Netlify
behave the same way by default. A red CI run therefore does **not**
stop a broken commit reaching production. Pick one:

1. **Protect the branch** — require the CI checks to pass before
   merging to `main` (branch protection or rulesets) and forbid direct
   pushes. The host still deploys on push, but only reviewed, green
   commits arrive. This is the cheapest fix and works on free tiers.
2. **Turn off automatic production deploys** and deploy from CI after
   the tests pass. Cloudflare Pages: *Build > Branch control*, disable
   automatic production branch deployments, then run
   `wrangler pages deploy` from the pipeline. A Pages project created
   with git integration cannot later be switched to Direct Upload, so
   decide early.
3. **Deploy only from CI from the start** (Direct Upload / CLI deploy
   with a scoped API token in the pipeline's secret store), with the
   usual environment approval for production.

Write down which model the project uses; "CI is green so it's safe" is
only true under 1–3.

## Platform-processed config files (`_headers`, `_redirects`)

- Cloudflare's `_headers` file: when the same header is applied twice —
  by duplicate lines or by two rules whose URL patterns both match — the
  values are **joined with a comma**, not replaced. Two
  `Content-Security-Policy` rules combine into one header containing
  both policies, which browsers enforce as *both* (the stricter
  intersection). Keep one CSP rule per path, and use the `! Header-Name`
  detach syntax to remove a site-wide header for a sub-path. Limits: 100
  rules, 2,000 characters per line.
- `_headers` does **not** apply to responses generated by Pages
  Functions or Worker code — set those headers in code.
- Local previews of a framework build (`astro preview`, `vite preview`,
  `next start`) do not apply the host's `_headers`/`_redirects`. Test
  CSP and redirects against a preview deployment or the live site
  (`curl -sI https://<preview-url>/ | grep -i content-security`), and
  add a post-deploy smoke check that asserts the header is present.

## Vercel specifics

- **Hobby (free) plan crons run at most once per day**, and timing is
  only per-hour precise (a `0 1 * * *` job fires between 01:00 and
  01:59). More frequent expressions fail the deployment. Use an
  external scheduler (a scheduled CI workflow hitting a protected
  endpoint) or the paid plan if you need more.
- If the project's **Root Directory** is set to a subfolder, run the
  CLI from the repository root. Running `vercel deploy` from inside the
  subfolder makes the platform apply the root directory again
  (`app/app`) and the build cannot find the project — observed
  behaviour (verify against your CLI version).

## Local green, CI red

When CI fails and the same tests pass locally, **diff the environments
before touching code**: a gitignored `.env.local` (or `.dev.vars`, or a
shell-exported variable) can satisfy a module-scope "required env var"
guard locally while CI has no such file, so every CI run fails at import
time. Check: env files present locally but ignored by git, tool
versions (Node/pnpm/Python), OS and path case-sensitivity, locale and
timezone, and cached build output. Fix by giving CI an explicit,
committed test environment (a `.env.test` with dummy values or
pipeline variables) rather than relying on whatever the laptop has.
